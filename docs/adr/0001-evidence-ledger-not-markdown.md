# 1. 用证据账本代替 Markdown 作为输出

日期：2026-10-28
状态：已采纳

## 背景

文档解析的默认产物是一段 Markdown——标题、段落、表格、公式按阅读顺序拼起来。
这对"给人看"很友好，但对"拿去用"很麻烦：

- 想知道某个数字是从原图哪读出来的，做不到；
- 想知道哪几个数字是机器没把握的，做不到；
- 想把结果导入 ERP，格式对不上，只能再写一个正则去猜哪些是金额。

更麻烦的是，一旦多个下游系统各自去解析这段 Markdown，每个系统都要重新
面对"这段文字可信吗"这个问题，而且答案还不一样。

## 决策

TraceCell 的主产物改成**证据账本**（`DocumentLedger`）。它是一张表而不是
一段文本，每个字段带三样东西：证据坐标、置信度、状态。

Markdown 仍然生成，但降级为账本的一种导出格式（给人看的复核报告），
不再是内部数据模型。

## 结果

- 字段能被锚定回原图区域：`match_region_for_value()` 先做归一化子串匹配，
  兜底用字符 bigram 相似度，阈值 0.55。
- 置信度可以按字段级别输出，而不是只有一个文档级分数。
- 导出 CSV 就是一份能直接进 Excel 的台账，正好对应"文档工具"赛道里
  "导出台账"这件事。
- 下游系统消费的是同一个账本，不会各自为政。

代价是数据结构变复杂了，多了一层"字段 → 区域"的绑定，以及绑定失败时的
"无证据支撑"状态。这个代价必须付，否则整个项目没有立足点。

## 备选方案

- **只输出 Markdown + 一个整体置信度**：实现简单，但解决不了"错在哪"。
- **只输出坐标不输出置信度**：能定位，但不知道该不该信。
- **输出带框的 HTML**：接近账本，但字段级置信度仍然缺，而且不好做机器消费。
