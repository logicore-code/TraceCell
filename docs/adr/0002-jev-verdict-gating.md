# 2. Jev 的 verdict 必须单独处理

日期：2026-10-29
状态：已采纳

## 背景

MiniCPM-OCR Jev 的官方文档里反复强调一件事：当调用云端 API、Docker 镜像
或带渲染器的 SDK 服务时，**必须检查 `verdict` 字段**。只有 `scored` 才表示
模型真的跑过了。图像编码失败、渲染失败、前向失败的情况下，服务会返回
固定值（0.0 或 -1.0 之类）。

这些固定值看起来像"极低的分数"，很容易被当成"模型认为这段识别错了"。
如果这么处理，后果是：

- 明明是服务挂了，所有区域都被判成低分，触发一轮无意义的重解析和升级复核；
- 账单上凭空多出一堆推理成本；
- 更糟的是，真正需要人看的区域被淹没在一堆假警报里。

## 决策

在数据层就把两种情况彻底分开：

- `Verdict.SCORED`：有真实分数，可以用。
- `Verdict.FAILED` / `Verdict.NOT_SCORED`：**分数一律丢弃**，置信度退回到
  保守缺省值 0.30，并在账本里标成"未参与评分"。

实现见 `types.py` 的 `Verdict`、`providers/jev.py` 的 `_to_result()`、
`risk.py` 的 `region_confidence()`。

## 结果

- 服务挂掉时，账本会诚实地显示"这一格没评上分"，而不是伪装成"识别错了"。
- 这个问题会被 `collect_findings()` 记成 `unscored_candidate`，运维能看见。
- 置信度计算永远只吃真正跑出来的分数。

## 备选方案

- **把失败当成 0 分处理**：简单，但会制造大量假警报，正是官方文档警告的那种用法。
- **失败时直接抛异常**：会让整个文档解析失败，连能用的部分也拿不到。降级比
  崩溃好。
