# 方法

TraceCell 想解决的不是"OCR 准不准"，而是**"识别结果能不能拿去签字"**。

这两件事的差距，就是企业和工具之间最贵的那段距离。一份发票识别错了金额，
如果没人知道错在哪，它就会一路流进账。对一个财务系统来说，最贵的不是
一次识别错误，而是**一次没人发现的识别错误**。

MiniCPM-OCR 1.0 已经是 SOTA 的解析模型，MiniCPM-OCR Jev 更进一步，能给出
区域级的正确性分数。TraceCell 做的是把这两块能力接上**业务决策**：分数
怎么变成"免检/抽检/全检"，低分区域怎么自己修好，修不好的时候该交给谁，
以及最后凭什么说这份文档"可以用"。

---

## 一、证据账本

普通的 OCR 输出是一段 Markdown。TraceCell 的输出是一张账本，每个字段都带三样东西：

| 东西 | 回答的问题 | 存在哪 |
| --- | --- | --- |
| 坐标 | 这个值是从原图哪一块读出来的 | `region.bbox` |
| 置信度 | 这块有多可信 | `field.confidence` |
| 状态 | 还需要人看吗 | `field.status` |

### 字段锚定

业务字段是从原文里抽出来的，要指回原文就得做一次匹配。TraceCell 用两步：

1. **归一化子串匹配**（优先）。把字段值和区域文本都做全角转半角、去空白，
   看是不是包含关系。命中后按"值占区域文本的比例"打分，最高 1.0。
2. **字符 bigram 相似度**（兜底）。子串匹配不上时退到这里，阈值 0.55。

匹配不上就**不绑定**。一个指错地方的证据比没有证据更危险——前者会让人
基于错误的定位做复核。

```python
# tracecell/ledger.py
matched = match_region_for_value("145,318.00", regions)
if matched is None:
    fld.region_ids = []          # 标记为"无证据支撑"
```

## 二、置信度继承

置信度不是模型直接吐出来的，是从支撑它的区域**继承**来的。

### 区域置信度

```
region_conf = max{ score(c) : c ∈ 候选且 c 已评分 }

若候选之间存在分歧：  region_conf ← region_conf × 0.65
若无候选评分：        region_conf ← 0.30（保守缺省）
```

分歧折扣的理由：两个候选不一致，本身就是不确定性的证据。这时取更高的那个
分是不诚实的。

### 字段置信度：悲观继承

```
field_conf = min { region_conf(r) : r ∈ 支撑该字段的区域 }
```

**取最小值，不取平均值。** 合同金额如果是从两个区域拼出来的，其中一处认错
了，这个字段就是错的。取平均等于把风险藏进统计里——而这个项目的整个目的
就是把风险显式化。

支撑区域全部缺失时，`field_conf = 0`，字段状态标成"无证据支撑"。

### 期望损失

```
expected_loss(f) = weight(severity(f)) × (1 - field_conf(f))

weight: critical 1.0 | high 0.55 | medium 0.25 | low 0.08
```

这个值不是概率，只用来在**同一份文档里横向比较**字段之间谁更值得多查一次。

## 三、对抗式核验闭环

Jev 只能告诉你"这段大概率不对"，不能告诉你"这段到底写了什么"。修复得
由系统自己去做，这就是闭环：

```
        ┌──────────────────┐
        │ 首次解析（4x 档） │
        └────────┬─────────┘
                 ▼
          Jev 打分 0.31
                 │
                 ▼
        ┌──────────────────┐
        │ 生成对抗候选      │  换 16x 档重解析 / 升级多模态复核
        └────────┬─────────┘
                 ▼
        ┌──────────────────┐
        │ Jev 择优          │  score_best：同区域多候选取高分
        └────────┬─────────┘
                 ▼
          0.88 ──► 放行
          0.22 ──► 仍存疑 ──► 升级 MiniCPM-V 4.7 ──► 再评分
                                     │
                                     ▼
                              还是不行 ──► 转人工（附裁剪图与全部候选）
```

**对抗候选从哪来？** 同一块内容用两套视觉参数各读一次。MiniCPM-V 4.7 支持
`4x` 与 `16x` 两档视觉 token 压缩：4x 保留更多细节适合密集文字，16x 更快。
两档读出来的结果不总是一致，差异恰恰是"这一格有歧义"的信号。

**升级复核问的是窄问题。** 不是"请描述这块内容"，而是"这块是 A 还是 B？
只回答正确的那个"。窄问题的答案短、可判定，可以直接变成新候选再交给 Jev
复评，形成闭环；散文不行。

## 四、逐格预算决策

这是 TraceCell 的大脑。每个区域在核验过程中都被问同一个问题：

> 现在停下的残余风险有多大？再花一次推理能换回多少？这次推理要花多少？
> 让人来看一眼又要花多少、换回多少？

### 动作空间

| 动作 | 成本（rcu） | 期望置信度增益 |
| --- | --- | --- |
| 放行 | 0 | — |
| 重解析 | 1.2 | 0.35 × (1 − c) |
| 择优 | 0.4 | 0.55 × (1 − c) |
| 升级多模态 | 3.0 | 0.65 × (1 − c) |
| 转人工 | 8.0 | 直接到 0.995 |

增益系数描述的是"换一种策略后这一格被纠正的概率"，离线样例和线上日志都
可以回归校准。

### 选择规则

对每个候选动作 a：

```
Δ(a) = weight × [ (1 − c) − (1 − c'_a) ]      风险下降
效率(a) = Δ(a) / cost(a)                        每单位成本的收益
```

取**效率最高**的可行动作。但有两道闸：

1. **预算约束**。总预算 `total_budget` 按风险分配：致命字段拿走 45%，
   高危 30%，中危 15%，低危 5%。超预算的动作标记为不可行。
2. **人工对照**。人工复核确定性强（0.995），但贵。如果

   ```
   (weight × (1 − 0.995)) / 8.0  >  效率(最优自动动作)
   ```

   就转人工。在低危格子上让人看是浪费；在高危格子上让人看可能比再跑三次
   模型更划算。

### 停止条件

- 置信度 ≥ `accept_threshold`（0.90）且候选无分歧 → 放行
- 轮次达到 `max_rounds`（3）→ 停止自动核验，转人工
- 残余风险 ≤ `residual_tolerance`（0.05）→ 接受现状

残余风险容忍度是**按风险等级自动换算**的：致命字段要 0.95 置信度才算免检，
高危要 0.91，中危要 0.80，低危只要 0.38。财务场景可以再调低，内部流转单据
可以放宽。

## 五、风险加权路由

粒度降到文档层，问题是："这份文件要不要人看？人看的话看哪儿？"

### 三档结论

- **免检（auto_pass）**：没有必须复核项，抽检也检不出有意义的东西
- **抽检（spot_check）**：整体可信，按抽样验收抽一部分
- **全检（full_review）**：高危字段大面积缺证据，或候选大面积打架

高危字段连原文都没找到时，直接判全检——那说明抽取这一环就坏了，整份台账
不可信。

### 抽样验收

抽检不是抽查个位数走个形式。设单件出错概率为 p，抽 m 件独立样本，至少
发现一处错误的概率是 1−(1−p)^m。要求不低于 1−δ：

```
m ≥ ln(δ) / ln(1 − p)
```

p 从区域置信度加权估计。这个式子直接给出"抽多少才够"，让抽检变成有统计
依据的动作。

### 定点复核清单

除了随机抽样，还有一份**必看清单**：所有期望损失超过容忍度的字段所依赖的
区域，加上所有候选互相打架的区域。清单里每一条都写清楚看什么、为什么看、
怀疑哪几个值——人不用回看整份文档就能开工。

## 六、单据内部勾稽校验

明细行加起来应该等于合计。这类矛盾**OCR 质量模型发现不了**——明细行和合计
行都识别正确，错的是单据本身。

做法分两步：

1. **抽明细**。明细行长得都差不多：一段标签加一个金额。用正则从区域文本里
   抽出 `(标签, 金额)`，字段名带 `明细:` 前缀。
2. **按单据类型声明勾稽关系**：

   ```python
   DEFAULT_SUM_RULES = {
       "expense": SumRule(total="金额", components=["明细"]),
       "invoice": SumRule(total="价税合计", components=["金额", "税额"]),
   }
   ```

   合计字段与明细字段都做金额归一化后相加，与合计字段比对，超出容差就生成
   一条 critical 级问题，两侧证据坐标一起带上。

之所以要按单据类型显式声明，是因为自动判断"哪些数是明细、哪些是科目"在
没有版面结构信息时不可靠——发票的表格里既有明细行也有小计行，凭正则猜会
误报。声明式规则把判断交给懂业务的人，代码只负责算。

## 七、跨文档对账

单份文档识别得再准，两份都识别正确但互相矛盾的情况照样会发生：合同金额
580,000，发票金额 518,000；合同乙方"南京海川软件股份有限公司"，发票上
"南京海川信息技术有限公司"。

OCR 质量模型解决不了这个——它只知道自己那一份看得对不对。对账必须放在
证据层：

1. 按字段名对齐两份文档的字段
2. 按类型归一化（金额去千分位、日期转 ISO、主体名去空格）
3. 比对，不一致就生成 Finding，两侧的坐标都带上

主体名称的比较用相似度阈值（0.85）而不是精确匹配：**"杭州明远科技"和
"杭州明远科技公司"在法律上是两个主体**，不该因为字面接近就放过。

## 开销

一次核验的成本分两块：

- **基础开销**：首次解析 + 首轮评分。无论策略怎么决策都会发生，省不掉。
- **额外开销**：重解析、择优、升级复核、转人工。受 `total_budget` 约束。

账本里会给出这两个数以及每个区域的花费，让"多查一次到底值不值"可以被
事后审计。

## 已知局限

说清楚边界比夸大能力有用：

1. **版面切分用的是自带的轻量实现**（投影法），不是 PP-DocLayoutV3。切分
   粒度是文本行级，遇到复杂表格和多栏排版会偏。接口是 `detect`，可以直接
   换成官方模型。
2. **置信度不是校准过的概率**。0.9 不等于 90% 正确。仓库提供了保序回归做
   校准，但需要自己标注一批数据才有意义。
3. **阈值必须自己标**。默认的 0.90 / 0.05 是通用起点，不是通用答案。
4. **重解析增益系数是估计值**。0.35 / 0.55 / 0.65 这几个数字来自工程判断，
   应当在自有数据上回归。
5. **对账只比字段值，不理解条款语义**。合同里"违约责任"条款写得含糊，
   两个值完全一致的合同照样可能有法律风险。TraceCell 解决的是"抄错"，
   不是"写得烂"。
6. **勾稽关系要手工声明**。当前只支持"若干字段之和等于另一个字段"这一种
   关系，且需要按单据类型配置。更复杂的勾稽（数量 × 单价 = 金额、
   含税价 ÷ 税率 = 不含税价）需要扩展 `SumRule`。
