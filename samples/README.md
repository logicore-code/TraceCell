# 演示样例

这个目录下的三张图是脚本合成的，不是真实票据。它们的作用是给回放模式
（`--provider replay`）提供一套图片与账本严格对齐的演示数据：JSON 里每个
区域的 bbox 就是图上那段文字的实际墨迹范围，点字段能直接跳到原图那一格。

## 重新生成

```bash
cd <仓库根目录>
python3 scripts/make_samples.py
```

脚本用 PIL + numpy 绘制，所有随机量（手写抖动、翻拍噪点、光照不均、旋转角）
都走固定 seed，每次执行产出完全相同的图片和 JSON。

| 文件 | 内容 |
| --- | --- |
| `samples/invoice_001.png` | 增值税专用发票，1240×1754 |
| `samples/contract_001.png` | 技术开发与运维服务合同，1240×1754 |
| `samples/expense_001.png` | 员工报销单，手机翻拍模拟：0.9° 旋转 + 噪点 + 亮度不均 |
| `samples/sessions/demo.json` | 与上面三张图一一对应的回放会话 |

`samples/real_ocr/` 里是 MiniCPM-OCR 1.0 在这三张图上的真实输出，录制命令见
`scripts/record_ocr.py`。

## 跑出来是什么

回放模式下跑完整链路（`tracecell demo` 或 `tracecell serve`）：

| 文档 | 区域 | 字段 | 待人工 | 成本 |
| --- | --- | --- | --- | --- |
| invoice-001 增值税专用发票 | 18 | 9 | 4 | 7.50 rcu |
| contract-001 技术服务合同 | 19 | 6 | 2 | 5.60 rcu |
| expense-001 员工报销单 | 17 | 9 | 2 | 6.60 rcu |
| 合计 | 54 | 24 | 8 | 19.70 rcu |

发票 9 个字段是 发票代码、发票号码、开票日期、购买方名称、销售方名称、
纳税人识别号、金额、税额、价税合计。报销单多出来的 3 个是明细行
（`明细:差旅费` / `明细:办公用品` / `明细:业务招待费`），勾稽校验要用。

## 每份样例埋了什么

### invoice-001 增值税专用发票

`r014` 是「价税合计（小写）¥145,318.00」。小写金额比标签小一号而且用浅灰印，
首轮识别只拿到 0.53 分——机器读对了，但它自己也拿不准。同一个区域的两条候选
给出两个数：`primary` 读成 `¥145,318.00`（0.53），`reparse-16x` 把 3 看成 8 读成
`¥145,818.00`（0.19）。系统没有硬选，两条都留在账本里，区域标成待人工。

同一区域还有一条 `vlm-review` 候选给出正确值 `¥145,318.00`（0.96），这就是
闭环里"问一句窄问题、拿一个可判定答案"的结果。另外 `r015` 备注区带一条
`failed` 候选，用来区分"没评上分"和"识别错了"——后者推不出前者。

最后 9 个字段里 7 个直接放行，`价税合计`（0.624）和 `销售方名称`（0.299）两格
进人工队列，原因写在区域的 note 里。

### contract-001 技术服务合同

`r009`「合同金额（大写）：伍拾捌万元整」印得偏淡，首次解析把"元"读成了"圆"
（0.24），重解析才读对（0.41），系统标成待人工而不是挑一个了事。`r010`
「合同金额：¥580,000.00」同样印得偏浅，首轮 0.38 分，重解析读成
`¥580,800.00`（0.19）。`合同金额` 字段因此停在 0.247。

大写和小写印的是同一个数（伍拾捌万元整 = 580,000.00），互为印证。

乙方名称是「南京海川**信息技术**有限公司」，发票上的销售方名称是「南京海川
**软件**股份有限公司」。两份文档各自都识别得没错，放在一起却对不上。

这里有个要说明的地方：对账模块按字段名对齐，发票叫"销售方名称"、合同叫"乙方"，
两个名字对不上，所以自动对账会把这对值列进 `single_source`（只有一份文档提到，
没法自动比对）。真正被机器自动报出来的金额矛盾在报销单那一份，见下。

### expense-001 员工报销单

整张图有 0.9° 旋转、轻微噪点和亮度不均，坐标跟着旋转一起变换，bbox 仍然贴着
文字。

`r011`「合计金额：¥2,864.50」印得又浅又小（0.37 分），重解析读成 `¥2,964.50`
（0.19）。而三条明细 `1,480.00 + 386.50 + 1,098.00 = 2,964.50`——单据上的合计
比明细之和少了一百块。勾稽校验会直接报出这条 critical 级问题，两侧的坐标都带
上。

`r003` 报销人「李思远」是手写体，重解析读成「李思源」（0.27），字段置信度
0.338。

发票的「金额」是 128,600.00，报销单的「金额」是 2,864.50，两份文档字段同名值
不同，对账模块会自动报出矛盾。

## 数据结构

`sessions/demo.json` 的格式由 `src/tracecell/providers/replay.py` 定义。

`bbox` 是归一化坐标（0~1，左上原点），由绘制时记录的像素坐标换算而来。
`category` 取 `text` / `table` / `figure` / `seal`。`candidates[].origin` 取
`primary` / `reparse-16x` / `vlm-review`，`candidates[].verdict` 取 `scored` /
`not_scored` / `failed`。

`fields[]` 里的字段名都能被 `src/tracecell/extractors.py` 的正则抽到，字段值是
对应区域原文里的子串——用正则抽一遍，结果与这里声明的完全一致。

`samples/labelled.json` 是标定用的"分数 + 人工判断"标注集，由
`scripts/make_labels.py` 从 `sessions/demo.json` 导出，判定规则是"候选文本与
区域原文一致就算对"，不看分数，所以不会循环论证。改了本目录的会话数据之后按
这个顺序重新生成：

```bash
python3 scripts/make_labels.py
tracecell calibrate samples/labelled.json
```

回放模式里的分数是录制时写死在数据里的，不是现场算出来的。要重新算就用
`--provider minicpm` 接上真实的 MiniCPM-OCR / Jev / MiniCPM-V 服务。
