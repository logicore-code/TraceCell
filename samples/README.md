# TraceCell 演示样例

这个目录下的三张图片是**脚本合成的样例票据**，不是真实票据，也不是从任何
真实单据上裁下来的。它们存在的唯一目的，是给回放模式（`--provider replay`）
提供一套**图片与账本严格对齐**的演示数据：JSON 里每个区域的 bbox 就是图片
上那一段文字的实际墨迹范围，点字段能直接跳到原图上那一格。

## 重新生成

```bash
cd <仓库根目录>
python3 scripts/make_samples.py
```

脚本用 PIL + numpy 绘制，所有随机量（手写抖动、翻拍噪点、光照不均、旋转角）
都走固定 seed，**每次执行产出完全相同的图片和 JSON**。

产出物：

| 文件 | 说明 |
| --- | --- |
| `samples/invoice_001.png` | 增值税专用发票，1240×1754（纵向 A4，150dpi） |
| `samples/contract_001.png` | 技术开发与运维服务合同，1240×1754 |
| `samples/expense_001.png` | 员工报销单，1240×1754（手机翻拍：0.9° 旋转 + 噪点 + 亮度不均） |
| `samples/sessions/demo.json` | 与上面三张图一一对应的回放会话 |

## 这批样例跑出来是什么

在回放模式下跑完整链路（`tracecell demo` / `tracecell serve`），得到的数字：

| 指标 | 数值 |
| --- | --- |
| 版面区域 | 54 个（发票 18 / 合同 19 / 报销单 17），全部带归一化坐标 |
| 业务字段 | 21 个（发票 9 / 合同 6 / 报销单 6），全部锚定回原文区域 |
| 自动定位的存疑区域 | 6 处（每份文档 2 处） |
| 核验成本 | 5.6 ~ 7.5 rcu / 份，均在 12 rcu 的预算之内 |

> 字段数是 21 而不是更多：三个 schema 的字段名合起来只有 21 个不重名的
> （invoice 9 + contract 6 + expense 6），`extractors.py` 按字段名去重，
> 同一份单据上买方的税号、双方的签署日期各自只留第一条。想要"每一处都
> 单独锚定"，看区域列表和 `region_ids`，不要看字段数。

`samples/labelled.json`（标定用的"分数 + 人工判断"标注集）是由
`scripts/make_labels.py` 从 `sessions/demo.json` 导出来的，判定规则是
"候选文本 == 区域原文就算对"，不看分数。**改了本目录的会话数据之后，
按下面顺序重新生成它**：

```bash
python3 scripts/make_labels.py                            # 重新导出标注集
tracecell calibrate samples/labelled.json                  # 重新标定阈值
```

## 每个 doc_id 演示什么

### `invoice-001`（增值税专用发票）

* **印刷难点**：`r014`「价税合计（小写）¥145,318.00」。小写金额比标签小一号
  且用浅灰印刷，首轮识别只有 0.53 分——机器读对了，但自己也拿不准。
* **候选打架**：同一块区域的两条候选给出两个不同的数——`primary` 读成
  `¥145,318.00`（0.53），`reparse-16x` 把 `3` 看成 `8` 读成 `¥145,818.00`
  （0.19）。系统没有硬选，两条都留在账本里，区域被标成待人工。
* **升级到多模态模型后修正**：同一块区域还有一条 `vlm-review` 候选，给出正确值
  `¥145,318.00`（0.96）——这就是闭环里"问一句窄问题、拿一个可判定答案"的
  结果。
* **没评上分的候选**：同一条区域还有一条 `not_scored` 候选（`¥145,318.OO`，
  Jev 评分超时）；`r015` 备注区带一条 `failed` 候选，用来区分"没评上分"和
  "识别错了"——后者不能从前者推出来。
* **字段置信度分层**：9 个字段里 7 个直接放行，`价税合计`（0.624）、
  `销售方名称`（0.299）两格进人工队列，原因写在区域的 note 里。

### `contract-001`（技术服务合同）

* **印刷难点 + 首次解析读错**：`r009`「合同金额（大写）：伍拾捌万元整」。
  大写金额印得偏淡，首次解析把"元"读成了"圆"（0.24），重解析才读对（0.41），
  系统标成待人工而不是挑一个了事。
* **候选打架**：`r010`「合同金额：¥580,000.00」同样印得偏浅，首轮 0.38 分，
  重解析读成 `¥580,800.00`（0.19）。`合同金额` 字段因此停在 0.247 的置信度。
  大写与小写两处印的是同一个数（伍拾捌万元整 = 580,000.00），互为印证。
* **跨文档矛盾**：合同上的乙方是「南京海川**信息技术**有限公司」，发票上的
  销售方名称是「南京海川**软件**股份有限公司」。两份文档各自都识别得没错，
  放在一起却对不上——这正是 `reconcile.py` 要抓的那类矛盾（值不同、主体名称
  相似度又不够）。
  注意：对账模块是**按字段名对齐**的，而发票叫"销售方名称"、合同叫"乙方"，
  两个名字对不上，所以自动对账会把这对值列进 `single_source`（只有一份文档
  提到，没法自动比对），矛盾由人在复核清单里一眼看出来——这恰恰说明为什么
  对账结论必须回到原图上核对。真正被机器自动报出来的金额矛盾，见下面
  `expense-001` 一节。
* 其余 17 个区域（条款正文、签署日期、两枚合同专用章）都一次读对，直接放行。

### `expense-001`（员工报销单）

* **翻拍噪声**：整张图有 0.9° 旋转、轻微噪点和亮度不均，坐标是跟着旋转一起
  变换的，所以 bbox 仍然贴着文字。
* **印刷难点 + 候选打架**：`r011`「合计金额：¥2,864.50」印得又浅又小
  （0.37 分），重解析读成 `¥2,964.50`（0.19）。而三条明细
  `1,480.00 + 386.50 + 1,098.00 = 2,964.50`——**单据上的合计比明细之和少了
  一百元**，账本会把这一格标成待人工，而不是替它选一个数。
* **自动报出的跨文档金额矛盾**：发票的「金额」是 128,600.00，报销单的「金额」
  是 2,864.50，两份文档字段同名、值不同，对账模块会直接报出矛盾并附上两侧
  的坐标与置信度。
* **手写体难例**：`r003` 报销人「李思远」是手写，重解析读成「李思源」（0.27），
  字段置信度 0.338。
* **低置信字段**：`金额`（0.240）、`报销人`（0.338）两格进人工队列，其余放行。

## 数据结构

`sessions/demo.json` 的格式由 `src/tracecell/providers/replay.py` 定义：

* `bbox` 是归一化坐标（0~1，左上原点），由绘制时记录的像素坐标换算而来；
* `category` 取 `text` / `table` / `figure` / `seal`；
* `candidates[].origin` 取 `primary` / `reparse-16x` / `vlm-review`；
* `candidates[].verdict` 取 `scored` / `not_scored` / `failed`；
* `fields[]` 里的字段名都能被 `src/tracecell/extractors.py` 的正则抽到，
  字段值是对应区域原文里的子串——用正则抽一遍，结果与这里声明的完全一致。

回放模式下的分数是录制时写死在数据里的，**不是**现场算出来的；真要重新算，
用 `--provider minicpm` 接上真实的 MiniCPM-OCR / Jev / MiniCPM-V 服务。
